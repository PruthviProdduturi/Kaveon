# Kaveon Engine benchmarks

These Criterion benchmarks measure Engine operators with deterministic input. They are performance tests, not correctness substitutes; the same workloads must also have automated result assertions.

## Run locally

From `engine/`:

```shell
cargo bench -p kaveon-storage --bench storage
cargo bench -p kaveon-exec --bench aggregate
```

The default data set contains 1,000,000 rows. Override it without changing the workload shape:

```shell
KAVEON_BENCH_ROWS=10000000 cargo bench -p kaveon-exec --bench aggregate
```

Criterion writes machine-readable estimates and HTML reports beneath `target/criterion/`. Retain the complete directory with every published result.

## Workloads

The storage suite measures full Parquet decoding, two-column projection, and row-group elimination. The execution suite measures:

- grouped `COUNT(*)`, `SUM`, `AVG`, `MIN`, and `MAX` at 16, 1,024, and 65,536 group cardinalities;
- a vectorized filter with approximately 50% selectivity;
- filter followed by arithmetic projection.

Every execution case uses 8,192-row Arrow batches. Values are generated by fixed integer formulas, so runs contain identical data without relying on a random-number generator or seed implementation.

## Fair PostgreSQL and Trino comparison

Do not compare Criterion's in-memory operator timing directly with a SQL server's network round trip. Cross-engine publication requires a separate end-to-end harness using the same persisted Parquet/Delta inputs and SQL semantics.

Only optimized release binaries are valid for performance comparisons. Debug-build timings are diagnostic evidence, never publishable benchmark results. In particular, timings captured from ordinary `cargo run` executions must not be compared with Criterion, PostgreSQL, or Trino results.

Record all of the following with a result:

1. Git commit and clean/dirty state.
2. CPU model, physical/logical core counts, RAM, operating system, and storage device.
3. Engine versions and complete configuration files.
4. Dataset generator version, row count, file count, compression, row-group size, and checksum manifest.
5. Warm-cache and cold-cache runs reported separately; never clear caches for only one engine.
6. At least five warm-up executions and thirty measured executions per query.
7. Median, p95, minimum, maximum, rows per second, and bytes per second.
8. Result checksums and row counts before accepting a performance sample.

Before recording latency, run the query correctness suite against the dataset and require identical typed results, including nulls and floating-point tolerance. The local reference scale currently includes 100,000 customers and 5,000,000 orders; smaller smoke datasets validate plumbing but do not support performance claims.

Use equivalent resource limits and concurrency. PostgreSQL must query equivalent typed relational data; Trino and Kaveon must read the same lake files. Report storage-only, execution-only, and client-observed end-to-end latency as different measurements. A benchmark is invalid if any engine returns a different result or silently uses an unsupported SQL rewrite.

The first cross-engine query set should include unfiltered count, selective filter, arithmetic projection, low/medium/high-cardinality group by, multi-aggregate group by, exact distinct count, equi-join, and grouped join. Unsupported queries must be labeled unsupported rather than omitted.
