# OpenSource product showcase

The showcase uses the `OpenSource` catalog in Kaveon Engine, backed by the ADLS
snapshot described in [OpenSource data](opensource-data.md). Saved datasets,
charts, and dashboard definitions currently remain in PostgreSQL. This showcase
does not complete the native transactional metadata migration.

## Open the portal

Sign in to Azure and select the test cluster, then keep this command running:

```powershell
kubectl --context kaveon-test-aks -n kaveon port-forward service/kaveon-portal 3000:3000 --address 127.0.0.1
```

Open `http://localhost:3000`, sign in with the approved Microsoft account, and open
**Dashboards**. Engine chart execution currently requires Analyst or Admin.

The [AKS validation record](../engineering/showcase-validation-2026-09-09.json)
contains the deployed image digests and live query evidence.

The initial snapshot collection covers NYC Taxi, WHO-reported COVID values, climate and energy,
and the archived Open LLM leaderboard. Each chart queries actual Engine data;
these are snapshot analyses rather than real-time feeds. Source caveats and units
appear in the dashboard descriptions and chart information tooltips.

## Recreate the showcase

From a checkout with Python, Playwright, and Azure CLI available, first validate
all source SQL without creating objects:

```powershell
python scripts/seed-showcase.py --portal http://localhost:3000
```

Then create or refresh the managed collection with an authenticated Admin:

```powershell
python scripts/seed-showcase.py --portal http://localhost:3000 --apply
```

The script uses the portal's Entra configuration, keeps authentication in memory,
and verifies generated chart SQL before publishing each dashboard. Reruns update
only objects with the managed showcase description; name collisions with other
objects stop the operation. It does not delete other dashboards or source data.

Chart definitions are in `scripts/showcase-queries.json`. Each saved SQL dataset
uses schema-qualified names and an explicit dimension and measure. Dashboard
charts intentionally have independent scopes; cross-filtering is disabled for
these aggregate snapshots. Open a chart to inspect or edit its query configuration.

The seed result report contains dashboard IDs and validation counts, without
credentials or data files. Browser validation must additionally confirm all chart
tiles render and refreshing the dashboard succeeds before declaring the
showcase ready.

## Original product dashboards

The original dashboard templates are preserved in
[`original-dashboard-templates.json`](../../data/dashboard-templates/original-dashboard-templates.json).
They are extracted from the repository's original seed scripts without connecting
to PostgreSQL or running their database mutations. The manifest records source
hashes. This is a repository snapshot, not an export of the current Vercel backend;
live Vercel parity requires a separate comparison with that backend.

The product family contains **Kaveon Product Usage**, **Kaveon Adoption &
Engagement**, and **Kaveon Platform & Growth**: ten charts per dashboard, original
layouts and palettes, and twelve filters covering license, audience, segment,
industry, platform, OS, region, country, team size, deployment, acquisition channel,
and date range. Each dashboard retains its synthetic-data notice.

The supporting `OpenSource.kaveon_product` schema is generated by
[`curate-kaveon-product.py`](../../scripts/curate-kaveon-product.py) in the
AKS curation Job. Its deterministic fixture contains 44,000 synthetic users and
230 days of usage, with 10.12 million daily usage rows. The materialized
`kaveon_product_analytics` table contains the same facts with user, geography,
and platform dimensions included. These are synthetic product examples, not
actual customer activity or a copy of Vercel's numerical results.

Parquet files and the generation manifest are uploaded to the existing private
ADLS snapshot under `kaveon_product/`. Temporary generation files disappear when
the completed Job is removed. This does not replace PostgreSQL product metadata.

After registering the Engine tables, use the importer to register the physical
analytics dataset and validate the original chart queries before publishing:

```powershell
python scripts/import-dashboard-templates.py --portal http://localhost:3000 --apply
python studio/qualification/rich_dashboard_browser.py --portal http://localhost:3000 --report tmp/dashboard-template-import-result.json
```

The importer preserves original chart and filter configurations while remapping
their dataset and chart IDs. Browser qualification additionally checks every
chart, all filter controls, value and date filtering, and restoration after Clear.
Do not treat SQL-only validation as proof of dashboard readiness.

The completed AKS evidence is recorded in
[`kaveon-product-showcase-validation-2026-09-09.json`](../engineering/kaveon-product-showcase-validation-2026-09-09.json).

The native reader currently needs a file location for each Parquet table. The
generator writes one file with bounded daily row groups and emits
`kaveon-product-singlefile-manifest.json`. An initial daily-file snapshot was
consolidated in AKS using `consolidate-kaveon-product.py`; its separate readable
manifest records the two combined fact files. Existing immutable files remain in
ADLS. After conditional catalog location updates, this test deployment required
a coordinator restart to refresh its runtime catalog snapshot.

Dashboard queries use a separate three-query Engine queue. The test Engine's
2 GiB admission budget reserves 512 MiB per query; sending six together exceeded
that budget. Temporary admission exhaustion now returns HTTP 429 with
`Retry-After`, and read-only chart requests retry with a bounded delay. The
relational backend retains its existing concurrency limit.

## Engine query boundary

The current Engine does not consistently resolve a derived table alias such as
`fact.pickup_date` over a saved aggregate SQL subquery. The showcase generator
uses unqualified columns for single-source Engine datasets. Engine datasets with
dimension joins must first be materialized into a single table. Other database
backends retain their normal qualification. Rankings sort by the projected measure alias because aggregate expressions
in `ORDER BY` also have an Engine resolution gap. General derived-table
alias and aggregate-sort support remain Engine compatibility tasks; the showcase is not evidence
of complete SQL or transactional parity.
