## Correctness finding

`SELECT DISTINCT platform ...` and filtered counts return values, but grouped
aggregates over dictionary-encoded `platform`, `deployment`, `segment`, and
some other low-cardinality columns return zero or incomplete rows. The query
detail for `GROUP BY platform` confirms all 504M rows were scanned and 24 local
groups were created per task, yet the final stage emitted zero rows. This is a
distributed aggregate/exchange finalization defect. No performance claim may
use those grouped results until result hashes and totals match a trusted
reference.

## Ordered improvement plan

1. **P0 — distributed aggregate correctness.** Add an end-to-end differential
   test over multiple workers for dictionary keys, plain UTF-8 keys, null keys,
   and mixed key types. Assert row counts, group keys, and aggregate totals at
   the final result, not only task-local metrics. Trace stage-1 merge output and
   exchange decode counts; the current detail shows stage-0 output rows and
   stage-1 output rows recorded as zero despite exchange payloads.
2. **P0 — benchmark validity.** Rebuild the exact v2 corpus predicates used by
   the Trino comparison, run three warm timed repetitions, and compare canonical
   result hashes. Record row groups read/pruned, bytes, CPU, exchange bytes,
   allocations, spill, and p50/p95. A query with an empty or partial result is
   a failure, never a speed win.
3. **P1 — typed dictionary aggregate path.** Replace per-batch text interning
   and string re-materialization with stable dictionary-code translation across
   batches and exchange partitions. Keep a safe fallback to decoded UTF-8 until
   the differential gate passes. This is the first new algorithm worth building:
   a global key dictionary plus compact integer group IDs.
4. **P1 — exchange final merge.** Make partial aggregate batches carry explicit
   row counts and schema/key metadata; validate decoded row counts before merge.
   Prefer fixed-width key/state buffers for integer-coded groups and avoid
   rebuilding `AggregateValue` objects in the final stage.
5. **P1 — scan/aggregation co-design.** Use exact footer statistics and row-group
   pruning before task admission; select local preaggregation only when the
   estimated group cardinality fits memory. For high-cardinality keys, use
   partition-local hash tables and bounded spill runs with a cost-based fan-in.
6. **P2 — hot-loop performance.** Profile CPU after correctness: dictionary-code
   hashing, UTF-8 decode, hash-table probes, and allocator time. Add SIMD/batch
   hashing and arena reuse only where profiles show material cost. Do not tune
   compression or invent a codec without exchange byte/copy counters proving it
   is the bottleneck.
7. **P2 — acceptance bar.** Require exact results, zero failed statements, no
   worker restarts, and a same-host comparison before claiming a Trino or
   ClickHouse win. Track scalar, low-cardinality, high-cardinality, joins, and
   concurrency as separate workloads.
