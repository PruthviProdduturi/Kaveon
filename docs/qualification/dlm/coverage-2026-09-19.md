# DLM coverage over an Engine table — 2026-09-19

Question-class coverage of the local stack's Engine-backed dataset, measured
with `python -m dlm.coverage --dataset 2 --markdown --questions --per-class 8`
(`api/dlm/coverage.py`). Every count is taken from the answer's
`evidence.lane`, which for an Engine-backed dataset is the Engine's own
`execution.mode` on the query record: `context` means the cube or the
statistics answered without reading the rows, `cache` the coordinator's
result cache, `live` the rows were read. Single runs on one laptop; the
millisecond columns are the API round trip as the harness saw it and are
not benchmark claims.

## Setup

- Local Compose stack ([guide](../../guides/local-stack.md)): coordinator
  and two workers built from `67075bd6`, the API from this branch.
- Dataset 2, **Product users**, bound to the Engine table
  `local-opensource-kaveon_product-kaveon_events_users`
  (`OpenSource.kaveon_product.kaveon_events_users`, one Parquet file,
  3,000,000 rows) with `source: {kind: "engine", table_id}`; metrics
  `Users = COUNT(*)` and `Locales = COUNT(DISTINCT locale)`; nine
  dimensions (`platform`, `license`, `segment`, `industry`, `region`,
  `country`, `deployment`, `acquisition_channel`, `team_size`); no date
  column, so the `year` and `trend` classes are not generated.
- Shape declared for the second run and its cube built (1,773 cells, one
  coordinator scan, 18–36 s):

```sql
ALTER TABLE OpenSource.kaveon_product.kaveon_events_users SET SHAPE (
    dimensions = ARRAY['platform:8', 'license:8', 'segment:8', 'industry:16', 'region:8',
                       'country:40', 'deployment:8', 'acquisition_channel:8', 'team_size:8'],
    measures   = ARRAY['locale:count_distinct', 'user_id:count']
);
ANALYZE OpenSource.kaveon_product.kaveon_events_users WITH (cube = true);
```

- The DLM regenerated after each shape change (`POST
  /datasets/2/dlm/generate?force=true`): 68 values indexed both times —
  from nine cube-shaped grouped counts under the shape (0.8 s), from nine
  bounded row-path scans without it.

## What the three non-answers are

- `two_filters` — "users in Free Enterprise": *Enterprise* is a value of
  `license`, `segment` and `team_size`, so the DLM asks which was meant
  (`reason: clarify`) rather than guessing. Correct behaviour, counted
  apart from refusals.
- `out_of_scope` × 2 — the weather and a poem are refused before any
  dataset is consulted (`reason: out_of_scope`). The class exists to show
  the refusal path is exercised.
- `unknown_value` × 2 are answered: a word that matches no indexed value is
  left out with a note in the answer ("Atlantis" matched no value of …),
  and the remaining question — the grand total — answers from the
  statistics. Whether a question with an unresolvable word should answer
  at all is a DLM policy item, recorded here as observed.

## Verified live

The reproduce block of a context answer, run through `POST /dlm/reproduce`
(`use_statistics = false`, `result_cache = false`), read the rows
(`execution.detail: "fragments; statistics bypassed"`, 452 ms) and returned
the same three cells the cube had answered for "users by platform in
Europe": Desktop 290,187 · Mobile 242,540 · Web 241,838.

## Observed on the way

Right after `ALTER TABLE … DROP SHAPE`, every distributed statement failed
for about a second with `NO_COMPATIBLE_WORKER: no active worker has catalog
snapshot sha256:…` while the workers caught up with the republished
snapshot; the DLM surfaced each as `reason: query_failed` and the harness
counted them as `failed`. The run above was repeated once the workers had
the snapshot. The bridge reports such a refusal to the client as "Engine
rejected the request" without the Engine's code; the code is on the
coordinator's audit ledger (`GET /v1/audit`).
