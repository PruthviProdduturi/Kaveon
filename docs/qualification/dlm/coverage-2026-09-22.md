# DLM question-class coverage over two Engine tables — 2026-09-22

239 questions across 21 named question classes over two Engine-backed
datasets on the local Compose stack — one with a declared shape and a built
cube, one with statistics but no shape — measured with
`python -m dlm.coverage --check` (`api/dlm/coverage.py`). 43 of those
questions also had their value computed by an **independent** statement this
harness wrote and ran through `POST /dlm/reproduce` (which forces
`use_statistics = false` and `result_cache = false`, so neither the cube nor
a cached result can answer it). **Wrong answers: 0 of 43 checked.**

Every lane count is the answer's `evidence.lane`, which for an Engine-backed
dataset is the Engine's own `execution.mode` on the query record: `context`
means the cube or the statistics answered without reading the rows, `cache`
the coordinator's result cache, `live` the rows were read. Single runs on one
laptop; the millisecond columns are the API round trip as the harness saw it
and are **not** benchmark claims.

This record supersedes the failure modes named in
[coverage-2026-09-19](coverage-2026-09-19.md): a question with an
unresolvable word no longer answers the grand total with a note, and a vague
question no longer falls through to the client's NL→SQL.

## Setup

- Local Compose stack ([guide](../../guides/local-stack.md)): coordinator and
  two workers, the Engine's insecure-development profile on
  `127.0.0.1:8081`. The API is this branch's `api/`, run beside the stack on
  `127.0.0.1:8083` against a PostgreSQL 17 metadata database for the DLM's
  own tables (`dlm_artifact`, `dlm_value_index`, `dlm_router`) and the two
  datasets below. Nothing in the Compose stack's own product state was
  written.
- **Dataset 3 — Product analytics (shaped).**
  `Kaveon.usage.kaveon_product_analytics`, one Parquet file, 10,120,000 rows,
  29 columns, `usage_date` 2026-01-01 … 2026-08-18 as text ISO days. Bound by
  `source: {kind: "engine", table_id: "local-kaveon-usage-kaveon_product_analytics"}`.

  ```sql
  ANALYZE kaveon_product_analytics WITH (sketches = true)          -- 5.2 s, full read on the workers

  ALTER TABLE kaveon_product_analytics SET SHAPE (
      dimensions = ARRAY['license:4', 'audience:4', 'segment:4', 'industry:12',
                         'team_size:5', 'deployment:3', 'acquisition_channel:5',
                         'platform:3', 'os:6', 'country:26', 'region:6'],
      measures   = ARRAY['queries_run:sum', 'errors:sum', 'sessions:sum',
                         'charts_created:sum', 'nl_queries:sum', 'sql_lab_runs:sum',
                         'dashboards_viewed:sum', 'api_calls:sum',
                         'user_id:count_distinct']
  )

  ANALYZE kaveon_product_analytics WITH (sketches = true, cube = true)
  -- 2,474 cells, one coordinator scan, 261 s
  ```

  The shape declares **no time axis**: `usage_date` is `Utf8`, and the Engine
  refuses a text time axis (`time 'usage_date' (Utf8) cannot be bucketed at
  day grain`). So the cube answers the dimension shapes and the DLM's time
  classes take the row path — which is exactly why the time classes below
  answer on `cache`/`live` rather than `context`.

- **Dataset 4 — Product events (unshaped).**
  `OpenSource.public.kaveon_events_dashboard`, one Parquet file, 10,120,000
  rows, 19 columns, no date column. `ANALYZE … WITH (sketches = true)` (4.1 s)
  and **no** `SET SHAPE`, so there is no cube. Bound by
  `source: {kind: "engine", table_id: "table:OpenSource:public:kaveon_events_dashboard"}`.

Each run was made with only that dataset's artifact compiled, so the router
had one dataset to choose and no question crossed over.

## What auto-curation derived, and from which statistic

Both specs were generated with no hand-written semantics at all
(`POST /datasets/{id}/dlm/generate?force=true`). What the Engine's record
produced:

| Element | Dataset 3 | Dataset 4 | Statistic |
|---|---|---|---|
| Dimensions | 13 (11 declared by the shape, plus `locale` and `platform_key` the statistics found) | 10 | `columns[].distinct` (HyperLogLog p=12) against `rows`; a declared shape wins |
| Cardinalities → `top_n` | license 4, audience 4, segment 4, industry 12, team_size 5, deployment 3, acquisition_channel 5, locale 26, platform_key 9, country 26, region 6, platform 3, os 6 | surface 6, platform 3, license 4, segment 4, industry 12, region 6, country 26, deployment 3, acquisition_channel 5, team_size 5 | the same distinct counts |
| Value index | 78 values | 74 values | only the dimensions the statistics call low-cardinality |
| Measures and ranges | 9 measures with p01/p50/p99 and exact bounds (e.g. `latency_p75_ms` min 50, max 3000, p50 1518, **outlier-safe max 2958**) | 9 measures, same shape | `columns[].quantiles` (KLL k=200) and `columns[].min/max` |
| Identifiers | none: `user_id` is 43,101 distinct of 10.12 M, below the 0.9 identifier ratio, so it is a measure | none | `columns[].distinct` ÷ `rows` |
| Time dimension | `usage_date`, 2026-01-01 … 2026-08-18, **grain `day`**, 229 periods, **latest `2026-08-18`** | none (no temporal column) | `columns[].min/max` on the temporal column — the maximum **in the data**, never `date.today()` |
| Evidence | every element carries `{statistic, basis, source_version, computed_at_ms, depth}` | same | — |

The probe that produced the distinct counts and quantiles was one
`SELECT APPROX_COUNT_DISTINCT(…), APPROX_PERCENTILE(…, ARRAY[0.01,0.5,0.99]) …`
answered by the Engine from its statistics (`execution.mode = "context"`,
8 ms on dataset 3). It is only sent when the record already carries every
sketch it names; a result whose record does not say `context` is discarded.

One curation edit was made, on dataset 4: its derived default metric is
`Rows` (`COUNT(*)`), and "total rows" ties with the `rows_scanned` measure, so
the DLM asks which — correctly, but it makes every question in the corpus a
clarification. `PUT /datasets/4/dlm/context` with
`{"default_metric": "actions"}` fixed it, and a later regenerate kept the
edit while refreshing every derived field.

The eight clarifications and six refusals are the point of the run, not a
shortfall:

- `breakdown` — "rows by platform key": `platform_key` and `platform` both
  read the phrase, so the DLM asks which.
- `two_filters` — "rows in Mid-Market Government": *Government* is a value of
  `industry` and *Mid-Market* of `segment`, but the pair is ambiguous against
  a second column, so it asks.
- `clarify_value` × 4 — "rows in Freezz", "rows in Consumzz",
  "rows in Mid-Markzz", "rows in Technolozz": each offers the nearest indexed
  value and an explicit "leave it out". For example
  `"Freezz" is not a value of surface, platform, license, … — did you mean
  Free?` with options `license=Free` and `skip`.
- `clarify_dimension` × 2 — "rows by colour", "rows by sprocket".
- `unanswerable` × 3 — "rows in Atlantis", "rows for Zorbo",
  "rows in Wakanda". **This is the 09-19 failure mode fixed**: the answer is
  now a refusal that names the closest questions the spec can answer, not the
  grand total with a footnote.
- `out_of_scope` × 3 — refused before a dataset is consulted.

Every class answered from the cube where the cube covers it: `breakdown`,
`filter`, `filter_breakdown`, `two_filters`, `top_n`, `share_of_total`,
`ratio`, `top_n_within` and `existence` all show
`cube at file (bb381666704c)`, and `distinct_total`/`distinct_breakdown`
add `(hyperloglog p=12)`. The **derived** classes are composed from those
cube answers — `share_of_total` is a cube cell over the cube's grand total,
`ratio` is two cube answers divided, `top_n_within` is one two-dimension cube
grouping ranked in Python, `existence` is one cube breakdown counted against
a threshold — so widening the class list did not cost the knowing path.

The time classes take the row path because the shape has no time axis:
`comparison_period` and `year_over_year` each run two windowed statements
(`cache` after the first run of each window), `trend` one.

## What this run does not cover

- **A cube with a time axis.** Both tables store their dates as text, which
  the Engine will not take as a time axis, so no time class was answered
  from the cube. A `Date32` or `Timestamp` column would put `time_slice`,
  `trend` and both comparison classes on the knowing path; that is the next
  thing to measure, not something this record claims.
- **A grain coarser than the data's.** "by month" over a day-grained column
  answers the daily series and says so
  (`usage_date is recorded by day, so the series is by day`). Bucketing a
  text date to months is not implemented.
- **`misclassified` 2 and 1.** The harness counts a question whose answered
  class differs from its corpus bucket. The three here are time questions
  over a single-period dataset answered as the ungrouped shape, which the
  harness's accept map already tolerates for `time_slice`/`trend`; the count
  is reported for transparency, not as a defect.
- Nothing here is a benchmark. Two Compose workers on one laptop, single
  runs, cold and warm caches mixed.
